# AI Visibility Audit — Scanner + Scoring + AI-Probe

Three independent agents (the first three of a planned 13 agent OPTWEB
system  TOFU acquisition, MOFU diagnosis, BOFU fulfillment, Retention ops)
that communicate through typed contracts:

```
Scanner Agent:   scan(url) -> Findings
AI-Probe Agent:  probe(business: BusinessIdentity) -> ProbeResult
Scoring Agent:   score(findings: Findings, probe?: ProbeResult) -> Scorecard
```

Each is a separate npm workspace package with its own test suite and `tsc`
build loop, importing nothing from the others — the only thing they share is
`@aiv/contracts` (`Findings`, `ProbeResult`, `Scorecard`). `probe` is
optional and additive to `score()`: omitting it reproduces the original
5-category, 100-point rubric exactly; supplying it adds a 6th `ai_visibility`
category and extends the ceiling to 120 (`Scorecard.total_score_max` always
reports which). The integration test (`integration/test/pipeline.test.ts`)
is the one place Scanner and Scoring are used together, proving the split is
clean by piping `scan()` straight into `score()` with neither agent aware of
the other's internals.

## Layout

```
packages/
  contracts/   Findings + ProbeResult + Scorecard types — single source of truth
  scanner/     scan(url) -> Findings          (Playwright + Lighthouse + JSON-LD)
  ai-probe/    probe(business) -> ProbeResult (queries ChatGPT/Claude/Gemini/Perplexity via Vercel AI Gateway)
  scoring/     score(findings, probe?) -> Scorecard  (pure rubric, zero LLM calls)
integration/   scan() -> score() piped across the full corpus, live
```

## Running things

```bash
npm install
npx playwright install chromium   # one-time, for Scanner

npm run test:scanner       # 76 tests, fast (frozen fixtures, no network)
npm run test:scoring       # 134 tests, fast, fully deterministic
npm run test:ai-probe      # 30 tests, fast (mocked network, no real API calls)
npm run test:integration   # 5 tests, ~3 min (1 live pipeline test + 4 fast reportTemplate tests)
npm test                   # all four, in order

npm run --workspace=@aiv/scanner corpus:run    # re-scan the live corpus,
                                                # refresh fixtures/corpus_findings/
npm run --workspace=@aiv/ai-probe corpus:run   # re-probe the live corpus,
                                                # refresh fixtures/probe_results/
```

Scanner's own test suite (`packages/scanner/test/corpus.test.ts`) runs
against **frozen** `fixtures/corpus_findings/*.json`, not live URLs, so
`npm test` is fast and deterministic. Those fixtures are regenerated by
`corpus:run` (a real Playwright + Lighthouse run against 9 real sites) —
re-run it and commit the refreshed JSON whenever an extractor changes in a
way that should shift real output. AI-Probe's test suite is fully mocked
(no real provider calls, no cost) for the same reason; its own `corpus:run`
hits the real Vercel AI Gateway and needs `.env.local` with
`AI_GATEWAY_API_KEY` (see "AI-Probe setup" below) — that fixture set hasn't
been generated yet (see "Known limitations" below). The integration test is
the one place that always hits the network, by design.

## Auditing a real website

This is the actual client-facing entry point — everything else in this repo
exists to support it. Two modes:

```bash
# Free, technical-only audit (Scanner + Scoring). No setup beyond "npm install".
npm run audit -- https://client-site.com/

# Full audit, adds AI-Probe (real ChatGPT/Claude/Gemini/Perplexity queries —
# spends real credit, needs AI-Probe setup below). All three business flags
# are required together; omit all three to fall back to the free mode above.
npm run audit -- https://client-site.com/ \
  --business-name "Client Business Name" \
  --business-category "plumber" \
  --business-city "Boise" \
  --business-region "ID"
```

Either way you get: a live scan, a score, a ranked fix list, an illustrative
business-impact projection, and an HTML report written to
`integration/reports/<slug>-latest.html` — open that file in a browser. Every
run also appends to `integration/history/<slug>.json`, so re-running the same
URL later automatically grows a score-over-time trend chart in the report.

**This is a normal Node project — it doesn't need VS Code, this chat, or any
particular terminal.** The whole thing lives at whatever path you cloned this
repo to. To run it from anywhere, independent of any one machine or editor:

```bash
git clone git@github.com:saurab200/OPTWEB-agents.git
cd OPTWEB-agents
npm install
npx playwright install chromium   # one-time
npm run audit -- https://client-site.com/
```

That's the whole setup. Any terminal on any machine with Node installed can
run it — Terminal.app, iTerm, a server, a scheduled cron job, whatever. If
you want a one-word command from any directory instead of `cd`-ing in first,
add an alias:

```bash
echo 'alias aiv-audit="npm run audit --prefix /absolute/path/to/OPTWEB-agents --"' >> ~/.zshrc
source ~/.zshrc
aiv-audit https://client-site.com/
```

**Cost note:** the free mode above costs nothing and never touches a paid
API. Only add the `--business-*` flags when you actually want the AI-visibility
check for a specific client — see `CLAUDE.md` for the full credit-discipline
rules this repo follows (caching, pacing, no wasteful re-runs).

## AI-Probe setup

AI-Probe queries all four providers through [Vercel AI
Gateway](https://vercel.com/docs/ai-gateway) rather than four separate
provider API keys:

```bash
vercel login                 # one-time, browser or device-code auth
vercel link                  # connect this repo to a Vercel project
# Enable AI Gateway + add a payment method at:
#   https://vercel.com/<team>/<project>/settings/ai
vercel env pull .env.local   # provisions VERCEL_OIDC_TOKEN automatically
```

A payment method on file unlocks the **$5/month free credit tier** (budget
models across all four providers, plus Claude Sonnet specifically) —
`AI_GATEWAY_API_KEY` in `.env.local` also works as a static alternative to
the OIDC token. Flagship models (`gpt-5-mini`, `gemini-3-flash`,
`sonar-pro`, etc.) require an actual paid top-up beyond the free tier, not
just a card on file — set a spend cap in the AI Gateway dashboard before
using them.

**Corpus fixtures not yet generated:** unlike Scanner and Scoring,
`packages/ai-probe/fixtures/probe_results/` is currently empty. Two real
`corpus:run` attempts (2026-08-09) both produced `probe_confidence: "low"`
results with 11-16 of 16 attempts failing — not committed as fixtures,
since flaky data would make the property tests flaky by construction. Once
a run comes back reliable, run `corpus:run` and add
`fixtures/probe_results/*.json`-based property tests following the exact
pattern in `packages/scanner/test/corpus.test.ts`; don't fabricate expected
fixture data in the meantime — that would violate the "real data, not
synthetic fixtures" principle this whole project is built on.

**Known limitation, discovered via two rounds of real testing, not
hypothetical — read this before spending more credit chasing it:**
1. Firing all `4 providers x 4 queries = 16` requests for one `probe()` call
   via a single `Promise.all` trips the free tier's rate limit even for
   models that succeed reliably one at a time. Fixed by bounding concurrency
   to 3 in-flight requests (`packages/ai-probe/src/concurrency.ts`).
2. Concurrency limiting alone was insufficient: a live run showed a business
   probed *second* in the same `corpus:run` fail on every provider,
   including one that had just succeeded 4/4 on the business probed first —
   the signature of a per-minute quota exhausting partway through a burst.
   Fixed by adding a paced delay (`REQUEST_PACING_MS`, default 500ms)
   between request starts, independent of the concurrency cap.
3. **Both fixes are real, tested, and correct — and a second live run after
   both were in place still failed at a similar rate** (a different mix of
   providers succeeded each time, ruling out a caching bug — it's genuine
   variable throttling). The Vercel Gateway error message is explicit:
   *"Free tier requests on this model are rate-limited. Upgrade to paid
   credits for unrestricted access."* Adjusting a spend cap or rate-limit
   setting in the dashboard is not the same as an actual paid credit
   top-up — only the latter appears to lift this restriction. If you've
   confirmed a real top-up (not just a cap change) and still see this,
   the next lever is a much longer `pacingMs` (multi-second, via
   `probe(business, { pacingMs: 3000 })`), trading a slower `corpus:run`
   for reliability — worth testing deliberately, once, rather than
   re-running the default repeatedly.

Response caching (`packages/ai-probe/src/index.ts`, `cacheTtlSeconds`,
default 24h via Vercel AI Gateway's `cacheControl` header) means none of
this costs *additional* credit on identical re-runs within the cache
window — the failures above are all first-attempt, uncached calls.

## Security

**Trust boundary: this tool has no SSRF protection, by design.** `scan(url)`
navigates a real Chromium browser and issues direct `fetch()` calls to
whatever URL string it's given — no allowlist, no denylist, and `fetch`
follows redirects. A URL like `http://169.254.169.254/latest/meta-data/` or
`http://localhost:6379/` is navigated exactly like any public site. This is
the same trust model as `curl`, a browser, or any local scraping tool: **only
run it against URLs you choose and trust.** Do not wrap `scan()` or
`integration/scripts/audit.ts` in a network-facing service that scans
arbitrary user-submitted URLs without first adding a private-IP/redirect
denylist — that turns this trust boundary into a real SSRF vulnerability
against your own infrastructure.

**Chrome sandboxing:** both the Playwright-driven browser and the
Lighthouse-driven Chrome instance (`packages/scanner/src/extractors/coreWebVitals.ts`)
run with the OS-level sandbox enabled (no `--no-sandbox`), since this tool's
entire job is rendering adversarial, attacker-controlled pages — exactly the
scenario the sandbox exists to contain. If a future deployment needs
`--no-sandbox` (e.g. running as root in a restricted container), that should
be a deliberate, documented choice paired with running scans in an isolated
environment with no access to secrets or the internal network.

**Known dependency issue, tracked not silently ignored:** `npm audit`
currently reports 17 moderate-severity findings in the
`@opentelemetry/core`/`@sentry/node` chain, pulled in transitively by
`lighthouse@12.8.2`'s internal error-reporting instrumentation — code this
project never configures or invokes directly (no Baggage-header parsing, no
HTTP server exposed). `npm audit fix` cannot resolve this without breaking
changes: `@sentry/node@9.47.1` pins `@opentelemetry/core` to `^1.30.1`, and
the fix requires `>=2.8.0`, so the only real remediation is a `lighthouse`
12→13 major-version bump, tracked as separate follow-up work rather than
bundled into an unrelated change. `npm audit` also flags 1 critical + 1 high
finding in `vitest`/`vite` — both are devDependency-only (the test runner's
optional UI dev-server), not reachable through `scan()`/`score()`, and not
exposed by anything this repo runs.

Same pattern in `packages/ai-probe`'s dependency tree: `@ai-sdk/provider-utils`
pins `undici` to `^5.29.0`, which cannot reach the patched 6.28+/8.x line
without `ai` and `@ai-sdk/gateway` themselves bumping a major version (6→7
and 3→4 respectively) — `npm audit fix` cannot resolve it non-breaking.
Practical risk is low: this `undici` instance is used exclusively as an HTTP
client to Vercel AI Gateway's own endpoint (`ai-gateway.vercel.sh`), never to
fetch attacker-controlled URLs and never as a server, which is the scenario
most of these advisories (request smuggling, header injection, WebSocket
DoS) actually require. Tracked as separate follow-up, not bundled here.

9 real, live URLs chosen to cover the categories called for in the build
brief:

| id | url | why it's in the corpus |
|---|---|---|
| `baseline-minimal` | example.com | minimal static page, no schema, no JS dependency |
| `content-heavy-ssr` | en.wikipedia.org/wiki/Web_scraping | large server-rendered text, no LocalBusiness schema |
| `js-heavy-spa` | excalidraw.com | canvas SPA — ~84% of visible content is JS-dependent |

| `well-optimized-commercial` | stripe.com | fast, has Organization (not LocalBusiness) schema |
| `partial-local-business-schema` | franklinbbq.com | real LocalBusiness JSON-LD, partial field completeness |
| `bot-blocking` | nytimes.com | robots.txt explicitly disallows GPTBot/ClaudeBot/anthropic-ai/Google-Extended/PerplexityBot |

| `login-walled` | linkedin.com/feed | unauthenticated request redirected to a login wall |

## Known scan-failure categories (Scanner)

Flagged honestly, per the build brief, rather than silently mishandled:

- **Login-walled pages.** The scanner has no auth story. It scans whatever
  an anonymous request sees (usually a login/signup page) and returns a
  `Findings` object describing *that* page — accurately, but it is not the
  real content. `scan_confidence` is not automatically downgraded for this
  case because nothing actually *fails*; there's no signal available to the
  scanner that distinguishes "this is a login wall" from "this business's
  homepage happens to be sparse." This is a real gap, not a false positive:
  a site behind a login wall will silently score based on its login page.
- **Anti-bot / headless-browser detection.** Some sites (Cloudflare-fronted
  sites in our corpus run) intermittently time out specifically on the
  JS-enabled Playwright render while a plain `fetch()` or the JS-disabled
  render succeeds — consistent with bot-fingerprint-based rate limiting or
  challenge pages that target headless Chromium. `scan_issues` records the
  timeout and `scan_confidence` drops accordingly; the guardrail (never
  return a fabricated number) held even before this was fixed — see
  `fixtures/scanner_failures/cloudflare-js-render-timeout.json`. This is a
  fundamentally unsolvable-by-us category for sites that specifically block
  automation.
- **Unusual JS frameworks / non-standard hydration.** The rendering
  extractor's heuristic (JS-on word count vs. JS-off word count) is a good
  proxy for typical SPA/SSR patterns but can misjudge frameworks with exotic
  hydration timing (e.g. content that streams in over many seconds past the
  `networkidle` + 500ms settle window). No corpus site exposed this, but
  it's a known blind spot — the 500ms settle window is a fixed, somewhat
  arbitrary constant (see judgment calls below).
- **Non-HTML responses (PDFs, downloads).** Navigating to a PDF or a
  direct-download URL causes Playwright's `page.goto` to reject with
  "Download is starting." Confirmed via manual probing (not in the
  committed corpus): the scanner does **not** crash — `scan_confidence`
  drops to `"low"`, every extractor short-circuits to its safe default, and
  the failure is logged in `scan_issues`. This is correct, guardrail-
  compliant behavior, just worth naming explicitly as a category the tool
  cannot meaningfully audit.
- **Rate limiting / CAPTCHA challenge pages that return HTTP 200.** The
  scanner has no way to distinguish "this is the real page" from "this is a
  bot-challenge page that happened to load successfully." Any structured
  data or accessibility signal extracted from a challenge page will be
  wrong but *confidently* wrong (`scan_confidence` won't be downgraded,
  because nothing threw). This is the sharpest edge of the guardrail: it
  catches crashes and timeouts, not semantically-wrong-but-successful loads.

## Judgment calls made during the build

Per the build brief's instruction to flag rubric or extraction decisions
that needed judgment rather than silently picking something — these are the
non-obvious calls, with rationale, all documented inline in code as well:

**Scanner:**
- `packages/scanner/src/extractors/schemaVocab.ts` — the "expected fields"
  list per schema.org type (e.g. `LocalBusiness` → name/address/telephone/
  openingHoursSpecification/priceRange/image/url/description/geo) is
  hand-built against schema.org's published vocabulary, since there's no
  reliable public API for Google's Rich Results Test. A different, equally
  defensible field list would produce different completeness percentages.
- `packages/scanner/src/extractors/accessibility.ts` — the four "canonical"
  landmarks counted for `landmark_coverage_pct` are banner/navigation/main/
  contentinfo; `search` and `complementary` are real ARIA landmarks but
  deliberately excluded since most small-business sites legitimately omit
  them, and counting them would penalize normal sites for a non-issue.
  `labeled_interactive_pct` is defined as vacuously 100% when a page has no
  interactive elements at all (a documented choice, not an oversight).
- `packages/scanner/src/extractors/contentExtractability.ts` — the
  hours/address/phone/services plain-text detectors are regex heuristics,
  tuned for readability over rigorous precision/recall. They will both
  under- and over-match on unusual phrasing.
- `packages/scanner/src/extractors/coreWebVitals.ts` — `inp_ms` is always
  `null`. INP is an interaction metric; a single-page-load Lighthouse run in
  navigation mode has no real user interaction to sample, so any number
  here would be fabricated. Nullable was explicitly allowed by the
  contract for exactly this reason.
- `rendering.ts`'s 500ms post-load settle window before measuring JS-on word
  count is a fixed constant, not derived from anything — a real tradeoff
  between scan latency and catching late client-side rendering.

**Scoring:**
- `packages/scoring/src/rubric/schema.ts` — `FaqPageFindings` (the Findings
  contract) carries no `fields_present`/`fields_missing`, only `present` and
  `question_count`, so the rubric's "proportional to field completeness"
  instruction has nothing to key off of for FAQPage specifically. Resolved
  by treating `question_count` as the completeness proxy (linear credit up
  to 4 questions). This is a substitution, not a literal reading of the
  rubric — flagged here as requested.
- `packages/scoring/src/rubric/accessibility.ts` — the rubric names three
  inputs (`landmark_coverage_pct`, `labeled_interactive_pct`, a flat penalty
  for heading problems) but not their relative weights. Resolved as an even
  7.5/7.5 split of the 15 points across the two percentage signals, with a
  single flat 4-point penalty applied once if *either* heading condition is
  violated (read as one combined penalty trigger, since the rubric phrases
  it as one flat penalty gated by an "or", not two stacking penalties).
- `packages/scoring/src/rubric/extractability.ts` — the rubric names
  `key_facts_in_plain_text` as primary and `avg_paragraph_word_count`/
  `qa_formatted_blocks` as secondary, without a split. Resolved as 7 of 10
  points for key-facts coverage, 1.5 each for the two secondary signals,
  with the paragraph-length full-credit threshold set at 15 words and the
  Q&A-blocks full-credit threshold set at 3 blocks — both arbitrary but
  documented constants.
- `packages/scoring/src/rubric/fixCatalog.ts` — the `ease` (1–3) rating per
  fix type is a hand-assigned lookup, not derived from any Findings field:
  e.g. "reduce JS dependency" is `1` (architecture-level effort) while
  "unblock a robots.txt rule" is `3` (a one-line config edit). This matches
  the brief's requirement that ease not be re-derived per business, but the
  specific 1–3 assignments are a judgment call.
- `packages/scoring/src/rubric/aiVisibility.ts` — `ai_visibility` (20 pts) is
  purely `overall_mention_rate`-proportional; mention *position* (named
  first vs. last) is deliberately not weighted in v1, since there's no
  real-world data yet on how much rank actually matters to referral traffic
  — baking in an unvalidated position-weight formula would be exactly the
  premature-precision this rubric otherwise avoids. This category also has
  no corresponding `top_fixes` entries: there's no direct lever for "improve
  ai_visibility" other than closing the gaps the other five categories
  already surface and re-probing later to confirm it moved.

**AI-Probe:**
- `packages/ai-probe/src/queries.ts` — four fixed query phrasings per
  business, to bound cost. A different set of phrasings would surface a
  different mention rate; these were chosen for how a real user casually
  asks an AI assistant for a local recommendation, not for statistical rigor.
- `packages/ai-probe/src/match.ts` — business-name matching is a
  case-insensitive, punctuation-stripped substring check, not fuzzy/edit-
  distance matching. Deliberately favors precision over recall (a false
  "mentioned" credit is worse than a missed one) — a business with a very
  generic name could be undercounted if the model's phrasing varies more
  than a substring match tolerates.
- `packages/ai-probe/src/providers.ts` — the default model per provider is
  whichever budget-tier model was confirmed accessible on Vercel AI
  Gateway's free tier at build time (2026-08-08), not necessarily the model
  a real user would actually be talking to (e.g. ChatGPT's actual default
  vs. `gpt-4o-mini`). Override via `probe(business, { models: {...} })` once
  paid credits allow higher-fidelity probing — see "AI-Probe setup" above.

None of these were "tuned to make a number look right" — each is documented
at its point of use with the reasoning, and the rubric was left as-is
whenever a surprising-but-correct result showed up in testing (e.g. Stripe's
`Organization` schema correctly scoring 0 on `local_business`, since
`Organization` is a schema.org supertype, not a `LocalBusiness` subtype).

## Regression fixtures (`packages/scanner/fixtures/scanner_failures/`)

Two real bugs were caught during the corpus build loop and are pinned as
permanent regression tests:

1. **`cloudflare-js-render-timeout.json`** — when the JS-enabled render
   timed out but the JS-disabled render succeeded, the scanner produced a
   physically inconsistent pair (`js_on_word_count: 0`,
   `js_off_word_count: 1109`), silently implying 0% JS-dependency by
   accident rather than by measurement. Fixed in `rendering.ts` by
   backfilling a failed side from the side that succeeded; regression test
   in `test/regression.test.ts` reproduces the exact shape with a mocked
   browser (no live-network flakiness in the pinned test).
2. **`robots-multi-agent-grouping.json`** — `parseRobotsTxt` mis-grouped
   consecutive `User-agent:` lines sharing one rule set, causing a bot to be
   reported `"allowed"` when its group's real rule set said `"disallowed"`.
   Fixed by rewriting the grouping to a simple two-phase state machine;
   pinned in `test/crawlerAccess.test.ts`.

Both were caught before ever producing wrong data in the committed corpus
fixtures — the full corpus was re-run after each fix to confirm no other
entry regressed, per the build brief's requirement.
